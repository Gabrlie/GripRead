# TXT encoding and reading tools

Status: implemented

## Problem

The M0 reader stored normalized UTF-8 text but could not recover the original bytes, change an imported TXT encoding, or provide durable first-class navigation tools. Long searches also needed cancellation so an old query could not keep competing with a newer one.

## Decision

Retain immutable source bytes under an asset-owned `sources/{asset_id}.txt` path and persist detected encoding, selected encoding, and replacement-character state in `txt_assets`. Automatic detection gives BOM and strict UTF-8 precedence, then uses `chardetng`; decoding uses `encoding_rs` and always normalizes line endings to LF. Normalized text, sparse UTF-16/byte indexes, and TOC entries are rebuildable products. Re-decode uses a blocking worker and schema-versioned `txt_decode_journal`: preparation reads and stages outside the application storage mutex, while a short transaction records the journal and metadata. Startup restores the old publication or completes a committed one before removing the journal.

TOC recognition is deliberately conservative for standalone Chinese `第…章/节/回/卷/篇` lines and English `Chapter` lines. Bookmarks are unique by book, content version, and UTF-16 offset. Literal search scans normalized UTF-8 in 64 KiB chunks, carries matches across chunk boundaries, returns UTF-16 locators and excerpts, and accepts an operation identifier that can be cancelled by the reader. These behaviors follow the reader contract and use Legado MD3's automatic encoding and per-book selection as an upstream reference ([commit 79678a6f9c589f6090f0b9f58bd7379acd2f8e93](https://github.com/HapeLee/legado-with-MD3/blob/79678a6f9c589f6090f0b9f58bd7379acd2f8e93/app/src/main/java/io/legado/app/model/ReadBook.kt#L1745-L1755)).

## Alternatives considered

Re-decoding in place was rejected because a process exit between file publication and the database commit could pair an old locator with new bytes. Keeping only normalized text was rejected because manual encoding correction would be impossible for older assets. Reusing page numbers or storing byte offsets as reader positions was rejected because layout and Unicode scalar boundaries are not stable.

## Consequences

Book and BookAsset identities survive encoding changes, while a changed normalized body receives a new content version and invalidates cached TOC and search locators. A normalized duplicate keeps the first asset's raw source and selected encoding. A missing legacy source remains readable; the reader can re-associate a candidate TXT only after its selected decoding reproduces the current normalized content. The current M1 UI reports old-version bookmarks as requiring re-location rather than silently moving them.

# WebDAV synchronization and backup

Status: planned

## Scope

Provide optional synchronization of structured reading records, a user-managed cloud book folder, and versioned backups. Local reading remains functional without WebDAV. These are separate user-facing capabilities; uploading a book is not the same operation as synchronizing its progress.

## Interfaces

`SyncService` handles replication, retry, conflicts, backup/restore, and cloud asset operations. `SyncStatus` exposes local-only, queued, syncing, synced, retry-needed, and conflict states without exposing credentials. Storage adapters supply explicit portable records rather than copying the live SQLite database.

## Behavior

### Data ownership

Automatically synchronize shelf records, groups, reading state, progress, bookmarks, source configurations, RSS subscriptions/groups/read/favorite states, and general preferences. Exclude embedded secrets from portable source configuration.

Never automatically upload chapter caches, RSS content/images, credentials, source login state, device paths, font files, per-device typography/window settings, or derived AI/vector indexes. Backups follow the same exclusions. AI-generated output is not added to synchronization until separately specified.

Use `/GripRead/Books` for user-selected TXT/EPUB uploads, `/GripRead/Sync/v1` for protocol records, and `/GripRead/Backups` for snapshots. Allow an existing book folder to be selected separately. Browse cloud files and download on demand; shelf replication does not imply the original book has been uploaded.

### Local-first replication

Persist domain changes locally before network work. When sync is enabled, store the change and durable queue record atomically so a crash cannot lose the pending operation. Coalesce progress uploads after 3 seconds of inactivity, with a maximum 10-second interval during continuous changes. Backgrounding and exit attempt a flush; interrupted work resumes later without depending on indefinite background execution.

Check remote records at startup, foreground entry, and book opening; while reading, check that book every 15 seconds. Also provide manual sync. Show local content immediately. If remote progress arrives after reading starts, offer a jump instead of moving the reader automatically.

Each device writes its own state records. All entities, including separately stored progress, carry causal versions and device provenance; removals carry tombstones. Use WebDAV reads/writes and conditional requests, validating server behavior before relying on it. There is no required push server. Protocol details are fixed with the sync implementation and versioned explicitly. See the [WebDAV standard](https://www.rfc-editor.org/rfc/rfc4918.html).

### With the GripRead server

设置 › 服务器 connects a device to the [server](server.md) with its address, its password (exchanged for a session token; the address and token stay in `sync-server.json` in the data folder, never in backups), and a device name. 断开 keeps the last sign-in (address, device name, password) in `sync-server-login.json`, also never in backups: the page fills it in, connecting again may leave the password empty, and 忘记登录信息 removes it. While connected, the server replaces WebDAV: backups, automatic backup, and progress sync pause and say so, their settings stay, and they resume after 断开. 云书架 then lists the server's book files (`GET /api/cloud/books`) with a 服务器 mark: 下载 fetches one into the ordinary import, 全部上传 queues the local books the server lacks for the next round, and books are not deleted there, since they leave the server with its shelf. While connected the same page also holds 自动下载服务器上的书, 通过服务器更新书籍, 同步内容 (the 同步排除 list seen the other way round: a row with the synced count opens a dialog with one switch per category, on meaning synced, so either page changes it), and the web version's 服务器账号 sections (定时追更, signed-in devices, 修改密码) reached through the core command `server_api`, which sends the device's session to an allowlist of management routes; a password changed there updates the kept sign-in. On first contact a preferences record that still holds a new library's defaults (a server never set up) does not replace the device's own settings, which go up instead. Sync carries what backups carry as records ([decision](../notes/implemented/2026-10-13-native-sync-records.md)): books by their file's hash and online books by name and author with their details, progress, bookmarks, and reading time, plus groups, replace and TOC rules, sources, and preferences (the shelf's layout and order, but not the group it shows, which stays each device's own). The 同步排除 list (the former 恢复忽略列表) keeps excluded categories local both ways. A record from elsewhere is merged field by field for books, online books, and preferences: a field comes in only when the other side changed it since the last sync, so a change made here meanwhile (允许更新 turned off) is kept and sent, and a server too old to know a field cannot clear it. An online book's details (signed addresses, the latest chapter, the introduction) do not count as a change of its record, which otherwise both sides would send back and forth after every refresh; only its source does. Replace rules arrive under their own ids. A record that cannot be applied is not marked synced, so it never reads as removed. Book files the server holds (not asked for after a push, or uploaded) are kept in `server_books` (schema 25) and shown as in the cloud on the shelf until 断开.

A round pulls what other devices and the web version wrote and applies it, fetches the covers and (with 自动下载服务器上的书, on by default) the books it names, then pushes what changed here and uploads the book files and covers the server lacks. Rounds run on events, not continuously: at connection (the server's records apply first, then this device's others go up), at start, on leaving and returning to the foreground, on a network change, when a book opens and when it closes, every 5 minutes while a book is open, on 立即同步, and 3 seconds after changes to what sync carries pause (at most 10 seconds during continuous changes). Reading itself (saved positions, reading time) and chapter downloads do not start a round (`api::starts_sync`); they go up with the next event. There is no long poll: other devices' changes arrive with those events. A failed round retries after 30 seconds, doubling to 5 minutes, and further changes wait for the retry; only events run sooner. An outage logs one warning, not one per round, and its end logs that sync recovered. Rounds keep one HTTP agent, so connections are reused rather than set up again per round, and a cover goes up only when the server lacks it (covers known to be there are remembered for the session). On Android, while the app is in the background (the system may cut its connections), a failed round is logged quietly instead of shown. Another device's position is never applied over this one: the reader offers it in the existing 跳转 prompt when the book opens or while it is open, and a device sends its position only when it is newer than the one synced. A book never read on this device takes the synced position directly.

Online books also carry their chapter list as a `chapters:online:<key>` record (category 在线书籍), so a directory updated on the server or another device arrives without asking the source. While connected and 通过服务器更新书籍 is on (the default; a device setting kept with the connection), 更新书架 runs on the server and its results come back as records, and each book's outcome marks it here (更新失败 with the server's reason, cleared once an update succeeds, even with no new chapters); the shelf's 自动更新 then only syncs to collect what the server's 定时追更 found, while pulling down and 更新目录 ask the server to update now. With it off the device updates from the sources itself; books the server lacks, or a failed request, update on the device. An uncached chapter is asked of the server first and of the source when the server cannot give it. Only a `text/plain` answer counts as a chapter, and a kept chapter file that holds an HTML page (an older server answered with its page) is deleted and fetched again. A server too old for 更新书架 (404 or 405) is noted in the log once per update, and the update runs on the device.

### Conflicts and failure

Apply causally ordered updates. Preserve conflicting values when the same field was edited concurrently. For divergent reading progress, show device, chapter, and text context and let the user choose; neither the furthest percentage nor wall-clock time wins automatically. Resolution creates a new causally related update.

Shelf removal propagates without deleting cloud originals. Cache cleanup stays local. Network/authentication/protocol failures retain local changes and retryable work; repeated delivery must not duplicate records. Keep status unobtrusive during reading and expose the cause, last successful sync, and retry action in settings.

### Backup and recovery

Create automatic snapshots daily when portable data changed, retaining the latest 7 automatic snapshots. Keep manual backups separately from automatic rotation. Snapshots contain versioned portable records and settings, not cached content or credentials.

A backup is one JSON document described by the [portable backup decision](../notes/implemented/2026-10-11-portable-backups.md): book records keyed by the SHA-256 of each book's original file, with progress, bookmarks, reading time, placement, metadata, and a cover reference, plus groups, chapter and replace rules, and preferences without device fonts or background images. Backups also carry the book sources as Legado JSON (login state and cookies stay on the device) and the online books on the shelf with their source details and their position and bookmarks by chapter (index, title, offset, chapter count); a restore adds sources that are missing or newer, matches online books by source address or by name and author, and places a restored position and bookmarks once the book's contents are fetched on first opening. The 恢复忽略列表 has 书源 and 网络书籍 entries. Everything lives in the application folder under the address (`GripRead/` unless 子文件夹 is set; an empty address uses 坚果云). Backups go to `Backups/` as `manual|auto-<UTC stamp>-<device name>.json` (the device name is editable), to an optional local backup folder (automatic backups replace one file there), or to a file the reader picks; covers go to `Covers/<sha256>.<ext>`. Restoring merges, skipping the categories in the device's 恢复忽略列表: matching books take the backup's metadata, cover, and placement, the newer position, the union of bookmarks, and the larger time of each day; records for books not on the device wait until a book with the same original file is imported. The cloud bookshelf uploads original files to `Books/` as `书名 - 作者.txt` with an index of hashes, titles, authors, introductions, and covers; uploading an uploaded book refreshes its information (after editing an uploaded book's details the app asks whether to, or does it without asking when 自动同步书籍信息到云书架 is on; it is off by default), and downloading fetches the complete file into the ordinary import, which matches it to the same book instead of adding a copy and then applies the indexed information. The shelf marks books the device last saw in the cloud. The WebDAV password, account, and switches stay in local storage; settings show the saved password on request, and the switches save as they change, leaving the account's 保存 for typed fields. Backup files the reader keeps (导出到文件 and the local backup folder) also carry the WebDAV address, account, password, and 子文件夹, which a restore takes only when the device has no account; backups sent to WebDAV never carry them. A connection check reports the median round trip and warns above 800 ms that progress sync is not recommended.

Progress sync follows Legado's 同步阅读进度 (on by default): opening a book fetches `Progress/<sha256>.json`, and leaving uploads the saved position when it changed; 同步增强 also does both when the reader returns from the background or the network comes back. Each record names the writing device's random id, name, and revision. A device ignores its own records and versions it already answered, and a fetch waits for that book's pending upload, so slow servers do not raise repeated prompts. An answer (jumping, cancelling, or closing) counts at once, so fetches queued before it do not ask again, and fetches asked for while one waits to start share it; the answered place is kept, and later versions from the same device are not asked about while it reads within a chapter of it (the next chapter of an online book, or about 10 000 characters of a local one). With the GripRead server the reader is told of a position only when a sync round brought that book's record; another device's different position asks whether to jump, as in Legado, showing the chapter each device is in and how many chapters apart they are. Positions relocate by context across different renderings of the book. Online books use `Progress/<hash of name and author>.json`, as Legado keys them by name and author, so a copy on another source still matches; their position is a chapter position mapped onto this device's contents. This replaces neither the causal replication described below nor its conflict handling, which remain planned.

Preview a backup, create a local recovery point (the five newest are kept, and each can be deleted on 备份与恢复), then apply the selected restoration as new synchronization changes. Reject unreadable or incompatible snapshots without damaging current state. Restore does not delete cloud originals or overwrite remote records as an unversioned database replacement.

## Acceptance

- Continue local reading and metadata edits without WebDAV and during connection failures.
- Switch devices, reread earlier passages, skew clocks, and create offline forks without silent progress loss.
- Interrupt/retry uploads and restoration; verify durable queue recovery, causal conflicts, tombstones, and idempotent record application.
- Transfer a manually uploaded book to another device while proving excluded data is absent from sync and backups.
- Test automatic retention, independent manual backups, preview, recovery points, and malformed backup rejection.
